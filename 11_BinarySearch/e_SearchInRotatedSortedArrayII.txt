================================================================================
QUESTION: Search in Rotated Sorted Array II with Duplicates (LeetCode 81)
FILE: e_SearchInRotatedSortedArrayII.java
================================================================================

1. WHAT IS THIS PROBLEM ABOUT?
--------------------------------------------------------------------------------
Search for a target in a rotated sorted array that may contain DUPLICATE elements. Return true if target is in nums, or false if it is not.

2. HOW TO THINK (INTUITION)?
--------------------------------------------------------------------------------
What goes wrong with duplicates?
Consider: [3, 1, 2, 3, 3, 3, 3]
`arr[low] == 3`, `arr[mid] == 3`, `arr[high] == 3`.
Because `arr[low] == arr[mid] == arr[high]`, we CANNOT determine which half is sorted!
The fix is simple and clever:
When `arr[low] == arr[mid] && arr[mid] == arr[high]`, just trim both edges: `low++` and `high--`!
This trims duplicates without skipping target (unless target was arr[mid], which we already checked).

3. STEP-BY-STEP APPROACH
--------------------------------------------------------------------------------
1. low = 0, high = n - 1.
2. while (low <= high):
   - mid = low + (high - low) / 2;
   - if (arr[mid] == target) return true;
   - if (arr[low] == arr[mid] && arr[mid] == arr[high]): low++; high--; continue;
   - if (arr[low] <= arr[mid]): // left half sorted
     - if (arr[low] <= target && target < arr[mid]) high = mid - 1;
     - else low = mid + 1;
   - else: // right half sorted
     - if (arr[mid] < target && target <= arr[high]) low = mid + 1;
     - else high = mid - 1;
3. Return false.

4. WHY THIS WORKS?
--------------------------------------------------------------------------------
Shrinking low and high removes identical edge values that obscure the rotation pivot, reverting back to standard rotated binary search.

5. WHY NOT OTHER APPROACHES (WHY NOT THAT)?
--------------------------------------------------------------------------------
Can we guarantee O(log N) in worst case?
No! In the worst case where all elements are identical (e.g. [1, 1, 1, 1, 1, 1]), every step shrinks by 1, resulting in O(N) worst-case time.

6. STEP-BY-STEP DRY RUN
--------------------------------------------------------------------------------
arr = [2, 5, 6, 0, 0, 1, 2], target = 0
low=0(2), high=6(2), mid=3(0)
arr[mid] == 0 == target -> FOUND! Return true!

7. COMPLEXITY ANALYSIS
--------------------------------------------------------------------------------
- Time Complexity: Average: O(log N), Worst: O(N)
  Reason: Average case divides in half; worst case (all duplicates) trims one by one.
- Space Complexity: O(1)
  Reason: In-place pointers.

8. IMPORTANT TIPS, TRAPS & EDGE CASES
--------------------------------------------------------------------------------
- Always check `arr[mid] == target` BEFORE doing `low++; high--;` so you never skip the target value.
