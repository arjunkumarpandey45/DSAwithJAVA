================================================================================
QUESTION: DQ13 - Find Minimum in Rotated Sorted Array II
FILE: DQ13_FindMinimumInRotatedSortedArrayII.java
================================================================================

1. WHAT IS THIS PROBLEM ABOUT?
--------------------------------------------------------------------------------
Given a sorted rotated array of integers 'nums' that may contain DUPLICATES,
return the minimum element of this array.
You must decrease the overall operation steps as much as possible.

2. HOW TO THINK (INTUITION)?
--------------------------------------------------------------------------------
In a rotated sorted array without duplicates, binary search compares nums[mid] with nums[high]:
- If nums[mid] > nums[high]: min must be in right half (low = mid + 1).
- If nums[mid] < nums[high]: min must be in left half (high = mid).
What happens when nums[mid] == nums[high] due to duplicates (e.g. [3, 3, 1, 3])?
We cannot tell which half the minimum is in!
However, we know that nums[high] is duplicate of nums[mid].
Even if nums[high] was the minimum, nums[mid] also has the same value!
Therefore, safely decrementing high (high--) eliminates the duplicate without losing the minimum.

3. STEP-BY-STEP APPROACH
--------------------------------------------------------------------------------
1. Initialize low = 0, high = nums.length - 1.
2. While low < high:
   - mid = low + (high - low) / 2
   - If nums[mid] > nums[high]:
     * Left half is sorted and larger; minimum is strictly to the right: low = mid + 1.
   - Else if nums[mid] < nums[high]:
     * Right half is sorted; minimum is at or to the left of mid: high = mid.
   - Else (nums[mid] == nums[high]):
     * Duplicate element: decrement high (high--).
3. Return nums[low].

4. WHY THIS WORKS?
--------------------------------------------------------------------------------
When nums[mid] == nums[high], either high is redundant (another identical element exists at mid),
or all elements in [mid..high] are identical.
In either case, discarding nums[high] preserves at least one copy of the minimum element in [low..high - 1].

5. WHY NOT OTHER APPROACHES (WHY NOT THAT)?
--------------------------------------------------------------------------------
Why can't we achieve O(log n) worst case?
- In an array with all identical elements except one (e.g. [1, 1, 1, 0, 1]), every mid returns nums[mid] == nums[high].
  Information theory proves that in worst case we MUST check every element, degrading to O(n).

6. STEP-BY-STEP DRY RUN
--------------------------------------------------------------------------------
Input: nums = [2, 2, 2, 0, 1]

Iteration 1: low = 0, high = 4. mid = 2. nums[mid] = 2, nums[high] = 1.
  nums[mid] > nums[high] (2 > 1) -> low = mid + 1 = 3.

Iteration 2: low = 3, high = 4. mid = 3. nums[mid] = 0, nums[high] = 1.
  nums[mid] < nums[high] (0 < 1) -> high = mid = 3.

Loop terminates (low == high == 3).
Return nums[3] = 0.

7. COMPLEXITY ANALYSIS
--------------------------------------------------------------------------------
- Time Complexity: Average O(log n), Worst Case O(n)
  Reason: Halves search range each step on average; reduces by 1 when duplicate values match high.
- Space Complexity: O(1)
  Reason: Only three pointer variables (low, mid, high).

8. IMPORTANT TIPS, TRAPS & EDGE CASES
--------------------------------------------------------------------------------
- high = mid (not mid - 1) because mid itself might be the minimum element.
- Comparing with nums[high] is safe for rotated arrays.
